# 方案：讓測試結果真正用於比較機制（待作者批准）

2026-11-22。只是方案，還沒有改 `mechcal/`。

## 1. 現狀（事實）

數據來自舊開發集運行（0.3.0，固定前三名、11 個家族）。分析腳本在會話暫存目錄，沒有新的模型調用。

| 觀察 | 數字 | 範圍 |
|---|---|---|
| 最終第一名和先驗第一名相同 | 92% | 50 次運行、10 個新開發集案例 |
| 有「有區分力」證據時，可信度的平均變化 | 論文支持的家族 +0.060；論文沒提的家族 +0.070 | 同上 |
| 計算型證據被標為「有區分力」的比例 | 16%（「部分」66%） | 1230 條 |
| 一次測試之後，被比較的家族朝相反方向移動 | 26% | 504 次測試、85 次運行（不用標籤） |
| 一次測試之後，被比較的家族都沒有移動 | 24% | 同上 |
| 被比較的家族平均移動幅度 | 0.031（超過 0.1 的只有 8%） | 同上 |

**代碼裡已經有「比較」的要求**：教授每次派測試都要寫 `separates`（至少兩個家族）和 `expectation`（每個家族預期看到什麼），見 `mechcal/agent/loop.py` 的 `Action`。

**缺的是後半段**：結果回來之後，沒有任何一步要求教授對照事先寫下的預期。`PlannerStep` 只有一段自由文字 `reading`。預期寫了，但沒有被用來判定。

## 2. 解讀

- 測試在形式上是比較型的，實際效果卻是「測什麼就確認什麼」：結果出來後，教授自由解讀，多數情況下可信度幾乎不動，或者被測的家族一起上調。
- 目前還**不能確定**的一點：工具算出的量本身是否帶有足夠的信息來分開機制。如果沒有，改教授的流程也不會讓答案更對。這個方案第 3 階段的檢查指標就是為了回答這一點。

## 3. 改動內容

### 改動 A：預期 → 判定（核心）

1. **教授在測試結果回來後的第一步，必須逐個家族給出判定。** 新欄位 `verdicts`，每個被比較的家族一條：
   - `outcome`：`as_expected`（符合預期）、`contrary`（與預期相反）、`inconclusive`（分不出）；
   - `basis`：依據的數值和它在記錄中的位置。
   - 失敗或被擋下的計算不給判定（失敗的計算不是證據）。
2. **假設板顯示每個家族的判定統計**（符合 / 相反 / 分不出各幾次）。只顯示數據，不規定可信度該怎麼改。
3. **Critic 多看兩件事**（由程序從記錄中找出，交給教授回應）：
   - 某次測試對所有被比較的家族給出同樣的判定，即這次測試沒有分開它們；
   - 某個家族的判定是「相反」，可信度卻上調了（或反過來）。
4. **提示詞**：說明 `verdicts` 是什麼數據；要求可信度的理由引用判定。不加任何「家族 → 測試」的對應，不規定更新公式。

不做的事：不加固定的更新規則；不改工具和能力卡；不改先驗的做法。

### 改動 B：新的提交格式（新指標本來就需要）

教授在假設板上給每個家族標記是否聲明（`claimed`），不再固定取前三名；被標記的家族按可信度排序就是答案（1–7 個，第一個是主要機制）。聲明哪些由教授決定，沒有固定門檻。Direct 和 ReAct 直接提交 1–7 個有順序的家族。（階段 1 已實現，2026-11-22。）

這一點會改變證據的作用：固定前三名時，證據要把排名翻過來才有影響；改成自選數量後，證據還決定邊緣的家族要不要聲明（對應 EVR 和 ES-Rec）。

## 4. 執行順序

| 階段 | 內容 | 驗證 |
|---|---|---|
| 1. 基礎 | `mechcal/eval` 讀 `rebuilt_302` 和新的劃分（`raw_v2_119` 及其校驗保持不動）；實現 6 個指標；新提交格式（改動 B），三種方法都支持 | 單元測試：指標文檔第 4 節的例子；隨機和固定答案的下限與指標文檔第 5 節一致；離線測試能產生並解析新格式 |
| 2. 基線 | 在新開發集（29 個，0141 除外）上跑現有行為的 MechCAL、Direct、ReAct，各 1 次，非高峰期 | 得到完整的 6 指標表和下面第 5 節的過程指標，作為對照 |
| 3. 改動 A | 實現「預期 → 判定」，先跑 1–2 個案例冒煙，再跑新開發集 | 和階段 2 的基線比較（第 5 節） |

階段 2 的粗估：MechCAL 每個案例約 0.8 M tokens、約 40 分鐘工具時間；28 個案例三種方法加評審，約 10–15 美元（非高峰期），並行跑一個晚上以內。開跑前我會再報一次準確估計。

## 5. 怎麼判斷改動 A 有沒有用

先看不依賴標籤的過程指標，再看 6 個指標：

| 指標 | 基線（舊運行） | 希望看到 |
|---|---|---|
| 測試後被比較的家族得到不同判定的比例 | 新指標，沒有基線 | 明顯高於「全部相同」 |
| 測試後被比較的家族朝相反方向移動的比例 | 26% | 上升 |
| 被比較的家族平均移動幅度 | 0.031 | 上升 |
| EP（證據精確率） | 0.77–0.79 | 不下降 |
| 重複運行的一致性 | 聲明集合完全相同 38% | 不下降 |
| 每個案例的 tokens | 約 0.8 M | 增加不超過約 10% |

**不採納的情況**：過程指標沒有改善；或者過程指標改善了，但 EP、一致性變差。ES-Rec、Top-1 等只作參考。

**如果移動變大了，答案卻沒有更對**：說明問題在工具本身的分辨力，下一步應該轉向檢查工具能提供什麼信息，而不是繼續改教授的流程。

## 6. 風險

- 教授可能把預期寫得很寬，讓所有結果都算「符合」。用「所有家族判定相同的測試比例」來監測。
- 只有 29 個開發案例，6 個指標的區間會很寬；所以用過程指標作主要判斷。
- 每一步多一個欄位，tokens 會略增。
