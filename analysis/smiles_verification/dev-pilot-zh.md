# SMILES 核實試點：17 個開發 case（2026-11-13）

## 結論

17 個開發 case 中 **13 個一致、4 個錯誤（24%）**。每個錯誤至少有兩個獨立來源支持；其中 3 個錯誤又被自動結構識別（MolScribe）獨立確認。

| case | 論文中的名稱 | 問題 | 依據 | MolScribe 第二次檢查 |
| --- | --- | --- | --- | --- |
| 0020 | CF3-HTTH | **取代位置錯**：CF3 應在 OH 的對位，SMILES 卻放在環連接處的對位 | 論文系統名、Fig. 1a、同系列 CF3-MTTH 的名稱 | 讀出的結構 = 更正後的 SMILES |
| 0141 | (2-ferrocenyl)indene | **少 2 個氫**：C19H14Fe，應為 C19H16Fe | 分子式計算；連接方式正確 | 讀不了（有機金屬） |
| 0152 | 2'-methyl-1,2-benzanthracene | **骨架錯**：甲基䓛，應為 2-甲基苯並[a]蒽 | 名稱、Fig. 1、PubChem | 讀出的結構 = 更正後的 SMILES（甲基位置也確認了） |
| 0153 | 3,4-benzopyrene | **分子錯**：苉（C22H14），應為苯並[a]芘（C20H12） | 原文「32 atoms and 90 normal modes」、Fig. 1、PubChem | 讀出的結構 = 更正後的 SMILES |

更正後的 SMILES 和全部依據見 `dev_pilot_results.json`。**case 檔案尚未改動。**

### 0141 的額外問題：三維結構

用 RDKit ETKDG（工具準備結構的方法）試了三種 SMILES 寫法，**都得不到二茂鐵的夾心結構**：

| 寫法 | 嵌入結果 |
| --- | --- |
| 現在的 case SMILES | Fe 只和兩個碳形成 σ 鍵（Fe–C 1.99 Å，其餘 ≥ 3 Å），不是夾心結構。**dev 運行用的就是這個幾何** |
| 離子式（氫數正確） | Fe 和環上原子只相距 0.6 Å，無意義 |
| η⁵ 配位鍵（10 條 Fe–C） | 嵌入失敗 |

所以 0141 只改 SMILES 不夠，結構準備這一步需要金屬茂的模板或原始幾何（例如晶體結構）。

## 方法

| 檢查 | 工具 | 結果 |
| --- | --- | --- |
| 分子式和高解析質譜 | `formula_check.py`（RDKit） | 4/17 有數據，4/4 一致。大部分數據在 SI，這次沒有 SI |
| 名稱解析 | `name_check.py`（OPSIN 2.8.0；常用名查 PubChem） | 10/17 解析出結構 |
| 結構圖比對（第一次） | Claude 看圖：原文結構圖對照 SMILES 繪圖 | 覆蓋其餘的 case 和錯誤複查 |
| **結構圖識別（第二次，自動）** | `ocsr_check.py`（MolScribe 1.1.1，只比較最大片段） | 13 個可讀：10 個和 case 一致，3 個和更正後的 SMILES 一致；1 個讀錯，3 個讀不了 |

MolScribe 不可靠的地方：
- **0009：讀錯。**羧基畫成彩色球棍原子，被讀成了硝基，骨架其餘部分一致。
- **0003、0056、0141：讀不了。**0003 的圖很小，還帶 OC10H21 縮寫和 Au；0056 的圖帶原子編號；0141 是有機金屬。

這 4 個 case 仍然以名稱、組成和人工看圖為準。

## 對開發工作的影響

- **0020、0141 在 dev1/dev2 算的是錯誤的分子**（0141 還是錯誤的幾何）。0152、0153 是新加入的開發 case。
- 按 24% 的錯誤率推算，102 個測試 case 中可能有 20–25 個 SMILES 有問題，必須在凍結和正式測試前處理。核實只用論文，不用 agent 的運行結果，所以不違反測試集鎖定。

## 推廣到 119 個 case 還缺什麼

1. **結構圖裁切。** 現在是人工看帶座標格的頁面來定框。批量時需要一個分子檢測模型（例如 MolDetect）自動裁切，再由人複查。
2. **補 SI**，讓分子式和質譜這一關能覆蓋大多數合成論文。
3. **每個 case 記錄 `smiles_origin`**：用了哪些來源、哪些一致。
4. **作者只看不一致的 case。**
